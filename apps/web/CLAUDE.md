# @bankql/web

TanStack Start (React 19) web app. Runs SQL queries against FDIC/NIC banking datasets in the browser via DuckDB-WASM, with TanStack Query managing async state, TanStack Table for display, TanStack AI for natural-language queries, and Chakra UI for components.

## Dev Commands

```bash
npm run dev        # vite dev (TanStack Start plugin handles route codegen)
npm run build      # vite build
npm run start      # vite preview
npm run typecheck  # tsc --noEmit
```

## File Layout

```
    _layout.tsx             # pathless layout route — wraps children in <Layout>
    _layout.index.tsx       # home route (/)
    routeTree.gen.ts        # auto-generated by tsr — do not edit
  lib/
    duckdb.ts               # getDB() singleton + runQuery() helper (no React context)
  domains/
    layout/                 # app shell (toolbar, sidebar + splitter, useLayout context)
    menu/                   # sidebar navigation
    agent/                  # AI chat — tool def, system prompt, useAgent hook, ChatPanel
    notifications/          # (empty for now)
  client.tsx                # client entry (hydrateRoot)
  ssr.tsx                   # server entry (createStartHandler)
  router.tsx                # createRouter() + type registration
vite.config.ts              # Vite 7 + @tanstack/react-start plugin — SPA preset
```

## Provider Stack

Providers are layered in `__root.tsx` in this order (outermost first):

1. `ChakraProvider` — Chakra UI v3 with `defaultSystem`
2. `QueryClientProvider` — TanStack Query client

DuckDB is NOT a provider. It's a bare singleton in `~/lib/duckdb.ts` accessed via `getDB()` / `runQuery()`.

## DuckDB-WASM Notes

- Lazy singleton: `getDB()` initializes on first call. `runQuery(sql, limit?)` handles connection lifecycle and caps rows (default 1000).
- Uses jsDelivr CDN bundles (`getJsDelivrBundles`) — no local WASM files to manage.
- `SharedArrayBuffer` is required; production COOP/COEP headers are set via `vercel.json`.
- `@duckdb/duckdb-wasm` is excluded from Vite pre-bundling (`optimizeDeps.exclude`) to avoid bundling its dynamic worker imports.
- `runQuery()` serializes BigInt → string and Date → ISO before returning, so results are JSON-safe.

## Routing

File-based routing via TanStack Router. Add a file under `app/routes/` and leave `npm run dev` running — the `@tanstack/react-start` Vite plugin watches and regenerates `routeTree.gen.ts` on change. Route files must export a `Route` const created with `createFileRoute`.

All user-facing routes nest under the pathless `_layout.tsx` route, which wraps children in the app shell (toolbar, sidebar, splitter with assistant panel). To add a new page: create `_layout.<name>.tsx` (or `_layout/<name>.tsx` directory form) rather than a top-level file.

This app is an **SPA-only frontend**. It does not run any server-side code. The agent chat endpoint lives in `apps/azf-v1` (Azure Functions).

## Agent

The AI chat agent lives under `app/domains/agent/` and is wired in via `ChatPanel` inside the right-side Splitter panel. Architecture:

- **Server** (`apps/azf-v1`): receives `{ messages }`, calls `chat()` from `@tanstack/ai` with the Anthropic-over-Azure-Foundry adapter, `query_data` tool definition (shared via `@bankql/schema`), and `buildSystemPrompt()`. Streams SSE.
- **Client** (`domains/agent/hooks/useAgent.tsx`): `useChat({ connection: fetchServerSentEvents(CHAT_URL), tools: clientTools(queryDataClient) })` where `CHAT_URL = import.meta.env.VITE_CHAT_URL ?? "http://localhost:7072/api/chat"`. The `query_data` tool executes in-browser against DuckDB-WASM — data never leaves the browser.

In prod the chat endpoint is served at same-origin `/api/chat` via Azure Front Door routing to the Function App. Set `VITE_CHAT_URL` accordingly (or leave unset to match same-origin).

## UI Guidelines

- Use **Chakra UI v3** for all UI. Prefer Chakra's compound component APIs (e.g. `<Menu.Root>`, `<Menu.Item>`) over the CLI-generated snippets.
- Keep in-component styling to a minimum — rely on Chakra's defaults. If you're passing more than a couple style props, that's a signal to step back and use a simpler composition.
- Use the base component with explicit props instead of shortcut variants:
  - `<Stack direction="row">` not `<HStack>`
  - `<Stack direction="column">` not `<VStack>`
  - This applies to all components that have similar directional or variant shortcuts.
- Prefer readability over conciseness. Spell things out — longer, clearer JSX is better than clever one-liners.
- Use `export default function ComponentName()` not arrow functions for component exports. Named function declarations are easier to identify in stack traces and React DevTools.
- Structure files to optimize for code splitting — one component per file, use lazy imports for heavy or route-specific code, and keep shared imports light so the bundler can split effectively.
- **Before implementing a UI component**, use the Chakra UI MCP to inventory available components that could solve the problem, then present at least 2 component approaches to the user for selection. For example, navigation could use `<Tabs>`, `<Menu>`, `<SegmentGroup>`, a `<Stack>` of `<Button>`s, etc. This is especially important during planning.
